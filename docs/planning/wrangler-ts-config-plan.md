# Wrangler TypeScript Config — Engineering Plan

Status: **draft for approval** · Owner: Engineering · Date: 2026-11-11
Scope: `wrangler` experimental `cloudflare.config.ts` / `wrangler.config.ts` adoption.

## 0. Corrections to the brief (verified in-repo)

Three input facts were wrong or incomplete. They change the cost model, so they are fixed first.

Two further repo facts that shape the plan:

- A **14th** `wrangler.jsonc` exists at `packages/cli/workers/trade-worker/wrangler.jsonc` — untracked and gitignored (`.gitignore:202`). Any glob-based generator must be allowlisted, not `find`-discovered.
- **Zero `env` blocks** exist in any of the 12 configs (`grep '"env"'` returns nothing).

## 1. Decision: prepare now, do not adopt

**Recommendation: do not adopt the experimental TS config now. Build the stable-path equivalent (Section 2), and re-evaluate when the format ships un-flagged.**

The deciding factor is that the headline benefit does not exist in this repo:

- The primary value proposition is `ctx.mode` branching replacing duplicated `[env.*]` blocks (CHANGELOG 4.100.0). This repo has **no `env` blocks at all**. The benefit is exactly zero today.
- Churn is not hypothetical. In **4.143.0** (PR #15914) the _Cloudflare_ helpers (`defineConfig`, bindings, triggers) moved to `cf/config`, forcing every adopter to add a new `cf` dependency — while `wrangler.config.ts` still imports `defineWranglerConfig` from `wrangler/experimental-config`. One project now spans two import paths. The feature landed in 4.100.0; it broke its own import path within 43 minor versions.
- The opt-in flag was renamed too: `--x-new-config` (added 4.100.0, PR #14202) last appears in 4.111.0 (PR #14652); `--experimental-new-config` is documented by 4.113.0. No changelog entry documents the rename itself, so the window is 4.111.0 → 4.113.0.
- The stability contract is explicit: "the flag, the config formats, and the `wrangler/experimental-config` exports may change in any release" (CHANGELOG 4.100.0).
- Adjacent churn is scoped but still real: 4.159.0 moves state to `.cloudflare/state` for the experimental `cf-wrangler dev` delegate only — direct `wrangler dev` still defaults to `.wrangler/state`. Generated types move to `.cloudflare/types/index.d.ts` (4.137.0) only when the experimental new-config path is enabled. This repo **commits 11 `worker-configuration.d.ts` files**, so any relocation touches every submodule.
- Blast radius is 12 files across **12 repos** (11 submodule repos + the parent repo, which owns `workers/dashboard`), and a second rename hits all 12 again. Per-file cost is trivial; _coordination_ cost is the real expense, and it recurs on every rename.
- Risk asymmetry is unfavourable: this is a live trading system. A config silently misread is a wrong deployment to `trade-worker` / `hoox-worker`, not a broken build.

The remaining benefits — typed config, computed values, DRY — are obtainable today on the stable JSONC path. That is where the effort should go.

## 2. What we can capture today (highest-value work)

### 2.1 Typed config source that generates the 12 JSONC files

Add a root-level generator, **not** in `packages/shared`:

```
scripts/deploy-config/
  manifest.ts      # allowlisted worker list + per-worker metadata
  configs/*.ts     # one typed object per worker
  generate.ts      # writes wrangler.jsonc, or --check for drift
```

**Why not `packages/shared`:** that package is published to npm (`shared-package-release.yml`, `npm-publish.yml`). Internal deploy topology (account IDs, KV namespace IDs, service bindings) must not ship in a public package. Root `scripts/` is not published and is already the convention here (`scripts/extract-graph.ts`, `scripts/typecheck-all.ts`).

Design constraints discovered during research:

- **Exclude `workers/dashboard` from generation.** `packages/cli/src/commands/deploy/deploy-command.ts:596-667` reads and atomically rewrites `workers/dashboard/wrangler.jsonc` `vars` at deploy time to sync service URLs. A generated file plus a `--check` gate would conflict on every deploy. Phase 1 generates 11 files and leaves dashboard hand-maintained; the CLI refactor to write into the TS source is a separate card.
- **Allowlist, never discover.** The manifest enumerates the 11 targets explicitly. A `find`-based scan picks up the stray gitignored `packages/cli/workers/trade-worker/wrangler.jsonc` and would rewrite it.
- **Never touch root `wrangler.jsonc`.** It is the CLI manifest parsed by `packages/cli/src/services/config/config-service.ts:74+`, not a worker config. (`packages/cli/src/index.ts:378` only checks that it exists.)
- **Operator comments must survive — or the loss must be an explicit decision.** 10 of the 12 configs carry operator instructions as `//` comments — **111** full-line `//` comments in total (113 including inline comments; counted per file with `grep -c '^[[:space:]]*//'`, so the figure is reproducible): `pyne-agent-worker` 42, `pyne-worker` 31, `telegram-worker` 12, `trade-worker` 12, `report-worker` 4, `dashboard` 3, `agent-worker` 3, `analytics-worker` 2, `email-worker` 1, `d1-worker` 1. A `jsonc.parse` → `JSON.stringify` round-trip deletes all of them, and byte-stable `--check` then makes the loss permanent. **Decision: preserve them.** Seed each generated file from the current source and emit the per-worker operator comment block verbatim (sidecar template, or hand-maintained block in the typed source); a plain parse/stringify generator is rejected. If deletion is ever chosen instead, it lands in the migration commit as a reviewable, explicitly-approved diff. Note that "no behaviour change" is true for wrangler semantics only — it is false for embedded operator docs.
- Generated files must be byte-stable (sorted keys, 2-space indent) so `--check` is a clean `diff`.

This delivers type safety, computed/derived values (e.g. service URL construction currently duplicated in dashboard `vars`), and single-source-of-truth across 11 files — the same three benefits — with zero experimental dependency.

### 2.2 `wrangler types --include-main-module=false` (4.159.0)

Relevant to **dashboard only**: its `main` is `.open-next/worker.js`, generated build output. The flag exists precisely for "Worker entrypoint is generated build output that should not be type-checked as application source" (CHANGELOG 4.159.0, PR #16066). It is preserved across `--check` and automatic regeneration. Low risk, do it in Phase 1. Note the caveat from the same entry: it opts out of module-derived `ctx.exports` typing while preserving runtime types, bindings, and DO namespaces.

### 2.3 `wrangler types --check` in CI

Viable, with two conditions:

- **Per-worker invocation only.** Multi-worker `-c` chaining was buggy and fixed twice — `--check` ignored secondary `--config` entries and `--env-interface` (CHANGELOG, PR #13572), then still mis-hashed secondary worker paths (PR #14034). Run `wrangler types --check -c workers/<name>/wrangler.jsonc` in a loop; do not chain `-c`.
- **CI must check out all 11 submodules.** `.github/workflows/ci.yml` currently initializes only 9 — `workers/pyne-worker` and `workers/pyne-agent-worker` are omitted. A `--check` loop must skip absent directories or the checkout list must be extended. Extending it is preferable but carries the token-permission caveat already documented in that workflow (`|| echo "::warning::..."`).

11 of 12 workers already have a committed `worker-configuration.d.ts`; only `pyne-worker` (Python) lacks one, which is expected.

### 2.4 Deprecated / removed behaviour audit

- `legacy_env` and service environments were **removed** in 4.111.0 (PR #14620) — including the field now raises an error. Repo scan is **clean**: no `legacy_env`, no service-environment usage, no `site` keys in any config.
- Real exposure is elsewhere: `workers/pyne-agent-worker/package.json` pins `wrangler: ^4.20.0` (predates every feature in this plan) **and** declares `engines.node >= 20`, contradicting the 4.159.0 floor. `workers/pyne-worker` pins nothing and runs `npx wrangler`, so its exposure is **already live, not a future risk**: every `dev`/`deploy`/`tail` resolves whatever wrangler is current, which is already past 4.159.0 and therefore already past the Node 22.12.0 floor. It does not wait for any upgrade step.

## 3. Readiness gaps (blockers before any adoption)

1. **Node 22.12.0 floor is unenforced and contradicted — but it is a warning, not a hard check.**
   - `.github/workflows/release.yml:62-64`, `npm-publish.yml:37-39`, `shared-package-release.yml:39-41,65-67` pin `node-version: "20"` — below the floor.
   - `ci.yml` has **no `setup-node` step at all**; it runs under Bun 1.4.4. There is no engine check to fail: `MIN_NODE_VERSION = "22.12.0"` in `wrangler-banner.ts` feeds a `logger.warn(...)`, so Node 20 CI warns and continues. That closes the Bun-shim question — there is no check for a shim to satisfy. The floor still matters as an _unsupported runtime_, not as a CI blocker.
   - No `engines` field and no `.nvmrc`/`.node-version` in the root.
2. **`^4.20.0` outlier + `engines.node >= 20`** in `workers/pyne-agent-worker` (Section 2.4).
3. **`pyne-worker` is unpinned, and its exposure is already live.** `workers/pyne-worker/package.json` has no `wrangler` dependency; its scripts shell to `npx wrangler dev|deploy|tail`, which resolves whatever wrangler is current on every invocation. That is already ≥4.159.0, so the Node 22.12.0 floor **already applies today** (as a warning) — this is a present risk, not a future one gated behind an upgrade step. **Recommended pin:** add `wrangler: ^4.159.0` as a devDependency and drop `npx` from the scripts (step 1.3), turning a floating runtime dependency into a reviewable lockfile change.
4. **Dashboard / OpenNext.** `@opennextjs/cloudflare ^1.20.13`, `main: .open-next/worker.js`, and bundling concerns split across the new model: `alias` and `assets.directory` are _tooling_ config (`wrangler.config.ts` territory per CHANGELOG 4.100.0) while bindings are runtime (`cloudflare.config.ts`). Whether OpenNext's build/deploy honours `--experimental-new-config` is **UNVERIFIED** — the changelog documents Vite `experimental.newConfig` and `cf-wrangler build` delegation, not an OpenNext path. Verify by reading `@opennextjs/cloudflare` release notes and testing a dry-run build.
5. **`pyne-worker` is Python** (`main: src/entry.py`). `cf-wrangler` exists "for projects that can't use `@cloudflare/vite-plugin` (service workers, old compatibility dates, Python, Rust, etc.)" (CHANGELOG 4.100.0, PR #14184) — but it is a **dev/build delegate for parent tools**, explicitly "a deliberately narrow CLI surface for a parent CLI to delegate to". It is not documented as a TS-config authoring path for Python workers. Treat "Python worker can use `cloudflare.config.ts`" as **UNVERIFIED**; verifying requires a dry-run with a `cloudflare.config.ts` present. Default assumption for planning: **exclude `pyne-worker`**.
6. **Submodule coordination.** 11 submodules means 11 commits + 11 pushes + 11 parent-ref updates. Safe order is dependency-first: leaves before the gateway, and `hoox-worker`/`trade-worker` last.

## 5. Risks and rollback

| Risk                                                      | Step    | Rollback                                                                                                                                |
| --------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Wrangler bump 4.152.0 → ≥4.159.0 changes deploy behaviour | 1.0     | Revert `bun.lock` + manifests; every worker still deploys on 4.152.0. Verify with `wrangler deploy --dry-run` per worker before merging |
| Node 22 bump breaks a Bun/Node-dependent script           | 1.1     | Revert workflow + `engines`; single commit                                                                                              |
| Generator changes config semantics silently               | 1.5     | `--check` seeded from current files makes this a no-op diff by construction; revert script                                              |
| Generator rewrites the stray `packages/cli/...` config    | 1.5     | Allowlist prevents it; verify manifest has exactly 11 entries                                                                           |
| Dashboard drift gate fights deploy-time URL sync          | 1.5/1.8 | Dashboard excluded in Phase 1 — no interaction                                                                                          |
| `--check` false-fails on CRLF checkouts                   | 1.7     | Fixed upstream in 4.156.1 (PR #16594); covered by the step 1.0 bump                                                                     |
| CI submodule token failures                               | 1.4     | Existing `                                                                                                                              |     | echo "::warning::"` guard keeps job green |
| Experimental rename hits 11 repos                         | 3       | Revert in **11 repos** + parent refs — the reason to defer                                                                              |
| Wrong config deployed to a live worker                    | 3       | `wrangler rollback` per worker; dashboard/gateway last                                                                                  |

Submodule rollback is the expensive one: it means a revert commit and push in each of 11 repos, then a parent ref update. This is the core argument for Phase 1 over Phase 3.

## 6. Open questions

1. **Where should the generator live — root `scripts/deploy-config/` (recommended) or `packages/shared`?** Default: root `scripts/`, because `packages/shared` is published to npm.
2. **Should `workers/dashboard/wrangler.jsonc` be generated in Phase 1?** Default: **no** — exclude it until `deploy-command.ts` writes service URLs into the TS source instead. Otherwise `--check` fails after every deploy.
3. **Is extending `ci.yml` to all 11 submodules acceptable**, given the documented token-permission caveat? Default: yes, with the existing warning fallback.
4. **Who owns the Phase 2 dashboard/OpenNext investigation** (gap 4 is the only genuine unknown that could block Phase 3)? Default: Engineering, as a timeboxed spike.
5. **Target re-evaluation trigger for Phase 3** — un-flagged config format, or a stated GA date? Default: re-evaluate when `--experimental-new-config` is removed from the changelog flag list, not on a date.
